# Contributing

1. Read `AGENTS.md`, the specification, architecture, security policy, and gotchas.
2. Open an issue for public behavior or option-schema changes.
3. Keep each pull request focused and add tests at the changed trust boundary.
4. Run `npm test` and `./scripts/build-release.sh`.
5. Update documentation and `CHANGELOG.md` when behavior changes.

Follow WordPress validation, sanitization, late escaping, capabilities, nonces, accessibility, and internationalization conventions. Runtime code stays dependency-free unless a major-version proposal demonstrates why this tiny matcher suddenly needs a supply chain.

Security reports belong in GitHub’s private vulnerability-reporting flow, not public issues.
